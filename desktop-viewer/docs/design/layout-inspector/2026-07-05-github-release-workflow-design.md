# GitHub Release Workflow Design

## Goal

Provide one GitHub Actions workflow that validates the repository, builds the
native Windows and macOS installers on matching GitHub-hosted runners, and
publishes both installers in one GitHub Release.

## Triggers

The workflow supports two release entry points:

- pushing a tag that matches `v*`, such as `v0.1.1`;
- manually running the workflow with a required semantic-version input, such
  as `0.1.1`.

A tag-triggered run publishes the pushed tag. A manual run creates or updates
the corresponding `v<version>` release tag from the selected commit. Ordinary
branch pushes and pull requests do not publish releases.

## Job Structure

The workflow contains four dependent stages:

1. **Resolve release metadata** validates the tag or manual input and exposes a
   normalized version without the leading `v`.
2. **Test** checks out the repository, configures JDK 21 and Gradle caching, and
   runs the complete Gradle test suite from `desktop-viewer`.
3. **Package** runs only after tests pass:
   - `windows-latest` builds the x64 MSI with `packageMsi`;
   - `macos-14` builds the x64 DMG with `packageDmg`.
4. **Publish** downloads both workflow artifacts and creates or updates the
   GitHub Release only after both native packages succeed.

Windows and macOS packaging remain separate jobs because `jpackage` produces
native installers only for the operating system on which it runs.

## Version Flow

The root Gradle build and Compose Desktop distribution accept an optional
`appVersion` Gradle property. When omitted, the checked-in default remains
`0.1.1`; CI passes the normalized release version explicitly.

Compose Desktop uses the semantic release version for the project and package
metadata. macOS receives a `jpackage`-compatible version whose first numeric
component is positive. For a release such as `0.1.1`, the macOS bundle version
is `1.1`, while the release tag and uploaded filename remain `0.1.1`.

The workflow rejects malformed versions before tests or packaging begin.

## Release Assets

Native outputs are renamed to stable, platform-explicit filenames before
upload:

- `AgentPerf-Inspector-<version>-windows-x64.msi`
- `AgentPerf-Inspector-<version>-macos-x64.dmg`

The package jobs first upload these files as workflow artifacts. The publish
job then downloads them and uses the GitHub CLI with the repository-scoped
`GITHUB_TOKEN` to create the release or replace assets on an existing release.
Release notes are generated by GitHub.

## Permissions and Security

- Test and package jobs receive read-only repository contents access.
- Only the publish job receives `contents: write`, which GitHub requires for
  creating releases.
- The workflow uses GitHub-maintained actions for checkout, Java setup,
  artifact transfer, and Gradle setup.
- No long-lived personal access token is required.
- Release publication is gated on successful tests and both native packages.

The initial workflow produces unsigned MSI and DMG files. Windows code signing,
Apple Developer ID signing, and notarization require external certificates and
secrets and are intentionally outside this change.

## Failure Behavior

- Invalid version input stops the metadata job with an actionable error.
- Test failure prevents all native packaging.
- Failure on either native runner prevents release publication.
- Missing package files fail their platform job rather than publishing a
  partial release.
- Re-running a release replaces installer assets with the same stable names
  instead of creating duplicate assets.

## Testing

Automated repository tests lock:

- both supported triggers;
- the least-privilege permission split;
- JDK 21 and Gradle setup;
- the complete test command;
- Windows and macOS runner/task selection;
- artifact filenames and release dependencies;
- default and CI-supplied version behavior;
- macOS version normalization.

Local verification runs the full Gradle suite and macOS DMG packaging. GitHub
Actions provides the authoritative Windows MSI verification after the workflow
is pushed and triggered.

## Alternatives Considered

### Separate build and release workflows

This provides more independent reuse, but introduces cross-workflow artifact
coordination and more state to maintain. One release workflow is simpler for
the current two-platform product.

### Build artifacts without publishing releases

This avoids write permissions but does not satisfy the requested automated
release workflow and requires manual asset handling.

## Non-goals

- Publishing on ordinary branch pushes or pull requests.
- Building Linux packages.
- Building separate Apple Silicon installers.
- Signing or notarizing native installers.
- Automatically pushing a new version tag from application source changes.
